# Deploying to school.ntsdigitalsolutions.com on Render

One Render **web service** (a Docker container) serves everything on one address:
`/api/*` → Django, everything else → the built React app. The database stays on **Neon**, uploaded
files on **Cloudinary**. Render provides HTTPS certificates and renews them for you.

```
Browser ──HTTPS──▶ Render (TLS) ──▶ container: gunicorn + Django + built React app
                                              ├──▶ Neon Postgres
                                              └──▶ Cloudinary / Brevo (email) / Daily.co (video)
```

Everything here that needs *your* accounts is marked **YOU**. Everything else is already in the repo
(`Dockerfile`, `render.yaml`, hardened production settings).

---

## 1. Put the code on GitHub  — YOU
Render deploys from a Git repository. The project has no commits yet.
1. Create a **private** repository on GitHub (e.g. `nts-school-system`). Turn on 2-step verification for your GitHub account.
2. From the project folder:
   ```bash
   git add -A && git status        # confirm NO .env files are listed — they must never be committed
   git commit -m "Initial commit"
   git branch -M main
   git remote add origin git@github.com:<you>/nts-school-system.git
   git push -u origin main
   ```

## 2. Database: promote the current Neon database to production  — YOU
You chose to keep the existing Neon database (it already holds your real accounts). Because that same
database URL currently sits in `backend/.env` on your computer, do this **before** go-live:

1. In the Neon console, create a **branch** of the database called `dev` (instant, copy-on-write). Put the *dev branch's*
   connection string in your local `backend/.env` from now on. Local work and the test-suite then can never touch production data.
2. **Reset the password** of the production database role in Neon (it has lived on your dev machine), and copy the new
   `DATABASE_URL` (ends in `?sslmode=require`) — you'll paste it into Render in step 3.
3. In Neon → Settings, raise **point-in-time restore / history retention** as far as your plan allows.
   Take a manual backup export now and store it somewhere safe.

## 3. Create the Render service  — YOU
1. <https://dashboard.render.com> → **New → Blueprint** → connect the GitHub repo. Render reads `render.yaml`.
2. Fill in the secrets it asks for (they are never stored in git):

   | Variable | Where to get it |
   |---|---|
   | `DATABASE_URL` | Neon production connection string from step 2 |
   | `CLOUDINARY_CLOUD_NAME/_API_KEY/_API_SECRET` | Cloudinary dashboard → **create new** production credentials |
   | `BREVO_API_KEY`, `BREVO_SENDER_EMAIL` | Brevo (verify your sending domain — see step 6) |
   | `DAILY_API_KEY` | Daily.co dashboard (only needed for live lessons) |
   | `SENTRY_DSN` | optional, for error alerts |

   `DJANGO_SECRET_KEY` is generated by Render automatically.
3. Click **Apply**. The first build takes several minutes. Database migrations run automatically each time the container starts
   (a failed migration stops the new version from starting, so the old one keeps serving).
   The blueprint uses Render's **Free** plan — see the note under step 3b.
4. When it is live, `https://<service-name>.onrender.com` shows the login page. Sign in with your existing platform-admin account.

### 3b. What "free" means on Render
- It costs nothing, and custom domains + HTTPS are included.
- The service **sleeps after ~15 minutes with no visitors** and takes about a minute to wake on the next request — the first person
  to open the site after a quiet period waits, then it is fast again. Fine for testing; for daily school use, switch `plan: free`
  to `plan: starter` (about $7/month) in `render.yaml` (or Render → Settings → Instance Type) to keep it always on.
- 512 MB RAM, no shell access, and no pre-deploy hook (that's why migrations run in `backend/deploy/start.sh`).
- Free web services get 750 instance-hours a month, which covers one always-on service; a sleeping service uses far less.

## 4. Point school.ntsdigitalsolutions.com at it  — YOU
1. Render → your service → **Settings → Custom Domains** → the blueprint already lists `school.ntsdigitalsolutions.com`
   (add it there if it isn't).
2. At the place that manages DNS for `ntsdigitalsolutions.com` add:

   | Type | Name | Value |
   |---|---|---|
   | `CNAME` | `school` | `<service-name>.onrender.com` |

   Remove any `AAAA` record named `school` (Render uses IPv4). If the domain is on **Cloudflare**, set this record to
   **DNS only (grey cloud)**.
3. Back in Render click **Verify**. It issues the HTTPS certificate automatically (a few minutes after DNS propagates).
4. Optional CAA hardening: if you add CAA records, allow **both** `letsencrypt.org` and `pki.goog`; a CAA record that
   allows only one CA can block certificate issuance.

## 5. Verify the deployment  — do every item
- `https://school.ntsdigitalsolutions.com` loads; `http://…` redirects to https.
- Browser dev-tools → Network → the document response has `content-security-policy`, `strict-transport-security`.
- <https://www.ssllabs.com/ssltest/> → **A/A+**; <https://securityheaders.com> → **A**.
- `https://school.ntsdigitalsolutions.com/admin/` shows the app (there is **no** Django admin login exposed).
- Sign in, refresh a deep page (e.g. `/students`) → still works; stay idle 30 min → signed out.
- **Client-IP check (important — controls rate limiting and audit-log accuracy).** From your own computer:
  ```bash
  curl -s -X POST https://school.ntsdigitalsolutions.com/api/v1/auth/login/ \
       -H "Content-Type: application/json" -H "X-Forwarded-For: 6.6.6.6" \
       -d '{"email":"nobody@example.test","password":"wrong-password-123"}'
  ```
  Sign in and open **Audit log**, find the newest `auth.login_failed` entry and read its `ip`.
  - It shows **your real public IP** (see <https://ifconfig.me>) → `TRUSTED_PROXY_COUNT` is right.
  - It shows `6.6.6.6` → lower `TRUSTED_PROXY_COUNT` by 1 (forgeable — fix it).
  - It shows a Render/Cloudflare address (same for everyone) → raise it by 1.
  Change it in Render → Environment, save (the service redeploys), and repeat the test.

## 6. Email (Brevo)  — YOU
Add and verify `ntsdigitalsolutions.com` as a sender domain in Brevo and add the SPF/DKIM records it shows to your DNS,
otherwise password-reset and invitation emails land in spam. Set `BREVO_SENDER_EMAIL` to an address on that domain.

## 7. Updating
`git push` to `main` → Render builds the new image, starts it (running migrations), and swaps over once it is healthy (a failed
build or migration leaves the old version running). To roll back: Render → **Deploys** → pick the previous one → **Rollback**.

## 8. Operations
- **Logs:** Render → **Logs**. Security events (`auth.login_failed`, `auth.account_locked`, …) are also in the in-app Audit log.
- **Backups:** Neon history (step 2) + an off-site export at least weekly. Test a restore once.
- **Rotate secrets** if anyone who held them leaves or a laptop is lost (DB password, Cloudinary/Brevo/Daily keys,
  `DJANGO_SECRET_KEY` — rotating that signs everyone out).
- **Never** run demo/seed commands or the test-suite against the production database (the seed commands now refuse to run
  unless explicitly forced in a DEBUG environment).

## 9. Before real student data goes in
Read `docs/SECURITY.md` (controls in place, and the honest list of remaining risks). Turn on 2-step verification for **every** account
that can reach the system: the domain/DNS host, GitHub, Render, Neon, Cloudinary, Brevo. Decide your data-protection duties for minors'
records (privacy notice, retention, breach process) — software cannot do that part.
